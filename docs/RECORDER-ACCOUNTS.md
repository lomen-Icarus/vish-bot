# Заявки студентов на запись своих пар — протокол записывалки и бота

Чтобы записывать пары, куда пускают только своих студентов, студент через бота
подаёт заявку со своей учёткой портала. Этот документ — договор между ботом и
записывалкой: по нему строится сторона бота (этап 2). Этап 1 (записывалка) уже
сделан.

## Как устроено

- **Слот = группа.** Одна учётка на группу (в общих лекциях потока на портале
  перечислены все его группы, поэтому учётка группы пускает и туда). Слоты
  живут в `data/accounts.json` на VPS (права 0600), не в `.env`: записывалка
  подхватывает их сразу, без пересоздания контейнера. Учётки владельца в `.env`
  остаются и идут первыми.
- **Пароль видит только записывалка.** В браузере студента (мини-приложение
  Telegram) логин и пароль шифруются открытым ключом записывалки. Бот хранит и
  передаёт только шифровку. Расшифровать может лишь записывалка — закрытый ключ
  лежит в `data/keys/accounts.key`, больше нигде.
- **Доверие** между ботом и записывалкой — общий `SLIDES_TOKEN` (тот же, что у
  слайдов), заголовок `Authorization: Bearer <SLIDES_TOKEN>`.

## Конверт (формат шифровки), v1

Случайный ключ AES-256-GCM шифрует `{"login","password"}` (JSON), сам ключ
шифруется RSA-OAEP-SHA256 (ключ 3072 бит). Дополнительные данные GCM (AAD):
`vish-rec|<telegram id>|<группа>`. Поэтому шифровку одной заявки нельзя выдать
за заявку другого человека или в другую группу.

```json
{ "v": 1, "k": "<base64 ключа AES под RSA-OAEP>", "iv": "<base64, 12 байт>", "c": "<base64 шифротекст+тег>" }
```

Открытый ключ (SPKI, base64) записывалка присылает боту в каждом отчёте
(`publicKey`). Мини-приложение берёт его у бота и шифрует им. В браузере —
WebCrypto (`crypto.subtle`), те же вызовы, что у записывалки.

## Ручки бота (их пишет этап 2)

Пока их нет, записывалка в ответ на `/rec/sync` получает 404 и тихо ждёт
(в логе один раз `debug`, без тревог). База — `BOT_SLIDES_URL` без `/slides`.

### `GET /rec/sync` → `{ "tasks": Task[] }`

```ts
type Task = {
  id: string;                 // id задания, вернётся в отчёте
  kind: "verify" | "install" | "remove" | "recheck";
  requestId: number;          // номер заявки в боте
  userId: number;             // telegram id подавшего (для AAD)
  group: string;              // группа, как назвал студент (бот подставил из профиля)
  codes: string[];            // коды для сверки со строками вебинаров: ["14-25"], ["11-23(эиэа)"]
  envelope?: Envelope;        // для verify и install
};
```

- `verify` — расшифровать, проверить вход в кабинет, доложить. Слот НЕ ставим:
  заявку одобряет человек. Расшифрованное тут же забывается.
- `install` — расшифровать и поставить учётку в слот группы (после одобрения).
- `remove` — убрать слот (отзыв студентом или админом).
- `recheck` — проверить «потерянный» слот заново.

### `POST /rec/report` ← тело

```ts
{
  publicKey: string;          // SPKI base64 — для мини-приложения
  results: { id: string; requestId: number; code: ResultCode; actualGroup?: string | null }[];
  slots: { group: string; status: "ok" | "lost"; lastOkAt: string | null }[];
  portal: "ok" | "down";
}

type ResultCode =
  | "login_ok"        // verify/recheck: вход прошёл
  | "login_failed"    // вход не прошёл (неверный логин или пароль)
  | "group_mismatch"  // (резерв) группа кабинета ≠ заявленной — бот сверяет сам по actualGroup
  | "portal_down"     // кабинет недоступен — не считать за плохой пароль, повторить позже
  | "installed"       // слот поставлен
  | "removed"         // слот убран (или его и не было)
  | "bad_envelope";   // шифровку не раскрыть
```

`actualGroup` у `login_ok` — группа студента по расписанию кабинета; бот сверяет
её с заявленной и показывает админу расхождение.

## Правила, которые держит записывалка

- **Проверка «аккаунт жив»** — раз в 6 часов. Заход на пару засчитывается за
  проверку. Сначала контроль — открывается ли кабинет; лежит — ничего не
  проверяем и мёртвым не объявляем. «Неверный пароль» дважды подряд (второй раз
  через 15 минут) → `lost`, и об этом один отчёт (на следующем `report` слот
  придёт со `status: "lost"`). Потерянный на пары не пробуется и не
  проверяется, пока не придёт `recheck` или `remove`.
- **До одобрения** расшифрованные логин и пароль нигде не сохраняются: `verify`
  раскрывает конверт, проверяет вход и забывает. На диск попадает только после
  `install`.
- **В логах** — номер заявки, группа, результат. Ни логина, ни пароля.

## Что сторона бота должна решить (этап 2)

- Лимит 2 заявки в месяц на telegram id; проверка подписи `initData` и свежести
  `auth_date`; срок жизни заявки (например, 7 дней) — если админ не ответил.
- Уведомления владельцу: новая заявка (с проверенным входом), переход слота в
  `lost`, отзыв. Студенту — нейтрально об остановке записи при потере доступа.
- Экран `/slots`: все слоты с группой, @ником, статусом, `lastOkAt`, кнопками
  «Отозвать» и «Проверить снова». Карта записи строится из этой же таблицы.
